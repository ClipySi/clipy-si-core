# ClipySi Core Interface Contract

This document summarizes the public contract for `clipy-si-core`. The source
code and the KAT vectors in `kat/` are the executable source of truth; this file
is the human-readable guide for host applications and future platform shells.

## Scope

`clipy-si-core` owns deterministic, cross-platform logic only:

- secret detection and display masking (`is_secret`/`mask`, plus the one-pass
  `evaluate` returning both the verdict and the display from a single detector run;
  the three are contractually equivalent and the KAT vectors pin all of them)
- local encryption/decryption helpers used by the app
- vault passphrase KDF and key derivation descriptors
- record envelope and vault manifest encoding/decoding
- sync hashes, HLC helpers, merge decisions, stale-device checks, and rejoin decisions

The core does not own I/O, storage, clocks, random nonce generation, networking,
Keychain access, UI policy, or logging.

## Invariants

- **Pure:** exported functions do not read files, open sockets, consult clocks, or use RNG.
- **No logging:** core crates must not call `println!`, `eprintln!`, `dbg!`, `log`, or similar APIs.
- **KAT-pinned:** observable behavior is pinned by `kat/*.json` and Rust/Swift conformance tests.
- **Forward-compatible:** public enums are `#[non_exhaustive]`; host apps must tolerate future cases.
- **Unicode-aware:** redaction spans are Unicode scalar offsets, end-exclusive.
- **Stable labels:** FFI exposes secret kinds as stable strings rather than exhaustive host enums.

## Host Responsibilities

Host applications must:

- generate nonces with a platform CSPRNG before calling seal functions
- store local device keys in platform-protected storage
- keep raw clipboard contents out of logs and diagnostics
- respect pasteboard privacy markers before invoking persistence
- run KAT conformance tests after changing bindings or release artifacts

## Swift FFI Contract

Swift consumers use `bindings/swift/ClipySiCore` as a local SwiftPM package.
`ClipySiCoreFFI.xcframework` is generated by `./build-xcframework.sh` and is not
committed. The generated Swift glue is committed and must stay in sync with the
Rust FFI surface; CI verifies this with `git diff --exit-code` after rebuilding.

The public macOS repository consumes the core as a prebuilt binary: this
repository's tag-driven CI builds the XCFramework, attests its build
provenance, and publishes it as a GitHub Release asset here, referenced by a
checksummed SwiftPM `binaryTarget(url:checksum:)` (with a git-ignored
local-XCFramework override for core development). Releases before v0.3.0
(`core-v0.2.0` and earlier) were published on the macOS repository instead and
remain there for reproducibility. The generated Swift glue committed in the app
repository must stay byte-identical to the copy in this repository. Publishing
a new core build means a new unique release tag/asset URL plus an updated
checksum — never overwriting a published asset.
